## Changes prepared in this pass

- Added owner cancellation for Pending and Approved appointments, scoped by the authenticated owner. The server recalculates the appointment start from its date and time in `Asia/Manila`, rejects starts inside the two-hour window or already started appointments, and updates only if the owner and original status still match.
- Added cancellation feedback and a cancel button that appears only while the client-side cutoff allows it. The API remains authoritative. Successful owner cancellation sends a separate, accurately worded confirmation through the existing Brevo adapter and logs the owner action.
- Replaced the appointment pet dropdown interaction with a native modal dialog showing only the signed-in owner's loaded pets, selection state, loading and empty states, and a link to register a pet.
- Added a persisted breed catalog API, owner searchable suggestions, admin list/search/filter/add/rename/enable/disable controls, normalized duplicate handling, audit logging, and an additive SQL migration. New administrator-created entries are unverified. Existing pet breed text remains untouched when entries are disabled.
- Added a separate append-only owner-reported weight history and form. Owner reports are labeled and dated in Asia/Manila. Existing `medical_records.weight` remains clinic-authored and unchanged. Pet deletion remains blocked when either history contains rows.
- Added styles to the existing Tailwind source and kept the current HTML, Express, repository, auth, and Supabase architecture.
- Tightened backend key selection: an unrecognized value is no longer accepted as a service key, and production startup now requires a recognized service-role key. The key itself is not logged or returned. The deployed Railway environment was not inspected.

## Source review for the breed starter catalog

The catalog must name the recognition scope rather than imply a universal list. The American Kennel Club describes its dog-breed index as its recognized breeds and currently states that it recognizes 200; the prepared migration includes only 48 AKC dog entries. FCI distinguishes definitive and provisional nomenclature; CFA publishes a recognized-breeds list. These lists differ in membership and status. The present catalog is deliberately identified as a starter subset and needs a clinic-approved scope and a fuller reviewed import before PetHub can claim complete recognized-breed coverage. Sources reviewed: [AKC dog breeds](https://www.akc.org/dog-breeds/), [FCI nomenclature](https://www.fci.be/en/Nomenclature/Default.aspx), [PCCI recognized breeds](https://www.pcci.org.ph/membership-or-registration/pcci-recognized-breeds/), [TICA breed standards](https://tica.org/breed-standards/), [CFA recognized breeds](https://cfa.org/breeds/), and [Feline Council of the Philippines recognized breeds](https://felinecouncil.ph/about/recognized-breeds/).

## Follow-up findings and implementation decisions

### Appointment cancellation

- The appointment repository stores and returns `appointment_date` and `appointment_time` as separate values. The backend and owner page interpret them as clinic wall time in `Asia/Manila`; the server recomputes the cutoff on each request and the database function rechecks it against PostgreSQL `statement_timestamp()` during the update. The UI also uses `Asia/Manila`; it does not use the browser's local zone for cancellation eligibility or deadline display. The live PostgreSQL column types and clinic's official timezone setting were not inspected, so confirm the schema stores these values as date/time wall-clock values before release.
- `Pending` and `Approved` are owner-cancellable. Exactly two hours before start remains eligible (`start - now >= 2 hours`). Less than two hours, the start instant, and later times are rejected. `Completed` and `Cancelled` are terminal and cannot be owner-cancelled. The database function filters by appointment ID, authenticated owner ID and the status previously read, and evaluates the exact cutoff in the same atomic update. If no row updates, the API rereads the owner's current row and returns the current state or a conflict. This protects requests across backend instances and the app/database clock boundary.
- The appointment row is updated to `Cancelled` and retained. The service sends an email and attempts an activity-log event; it does not delete the appointment or change it to `Completed`. The activity logger catches write errors, so its timestamp is best-effort rather than transactionally guaranteed. No cancellation reason is collected or needed for the cutoff. No dedicated `cancelled_at`/reason column is selected or written by the application, and the live schema was not inspected. If the clinic requires durable cancellation-event timestamps, first verify whether a status-history table/trigger already exists; otherwise propose an additive `cancelled_at timestamptz` written in the same conditional update. No such migration is prepared because the actual schema is unverified and the current flow does not need the field to enforce the cutoff.
- Repeated requests that find the row already cancelled return the existing cancelled row as an idempotent response; only one request performs the state transition, notification, and log attempt. Concurrent tests cover one transition and one email. The second response is not a second transition.
- The owner card now displays the exact cancellation deadline in clinic time and a reason after the cutoff, after start, for an invalid clinic time, or for a terminal status. The client check is advisory; the server remains authoritative.

### Medical record association correction

The initial implementation reconstructed `appointment_id` from an activity-log action and returned it as though it were stored. That was not a reliable relationship. The current code no longer treats logs as proof of a link and no historical rows are updated. `medical_records.appointment_id` is now selected, validated, and inserted as an explicit relationship. The prepared migration's foreign key and unique partial index enforce a maximum of one linked record per appointment. A completed appointment with a matching `pet_id` is required; an appointment without `pet_id` is not linked by name or by selecting a different pet.

Unlinked historical medical records stay unlinked. If the same pet has an unlinked record, or a legacy activity entry names the appointment, the admin views show “Relationship unresolved” and the API refuses a new appointment link pending clinic review. A log-query failure also leaves the relationship unresolved rather than claiming no record exists. The log is used only to raise an ambiguity flag, never to synthesize `appointment_id`. Standalone records without an appointment remain allowed through the API. Appointment approval or completion never creates a medical record.

The current form and duplicate checks support one official medical record per completed appointment; the clinic should confirm this policy before applying `2026-10-22_medical_record_appointment_link.sql`. If a visit may create multiple independent official records, do not apply the unique index as written; use a different association model (for example, multiple records per appointment with a non-unique FK) after the clinic defines the intended record lifecycle.

## API changes

- Added authenticated owner endpoint `POST /appointments/cancel/:id`. It returns 404 for an appointment outside the token owner's scope, 409 for cutoff or status conflicts, 503 if the required reviewed database function is absent, and does not delete or auto-complete an appointment.
- Added authenticated owner catalog endpoint `GET /pets/breeds?species=Dog|Cat` for active breeds.
- Added admin-only catalog endpoints `GET /admin/breeds?species=...`, `POST /admin/breeds`, and `PUT /admin/breeds/:id` for search/list, add, rename, enable and disable.
- Added owner write endpoint `POST /pets/:id/weight-reports`; pet history now includes separate owner-reported snapshots and reports whether that migration is available.
- Modified `GET /admin/dashboard/overview` and `GET /admin/dashboard/appointments` to expose only explicit medical-record links and an unresolved relationship state; old logs are warning evidence only.
- Modified `POST /admin/dashboard/medical-records/create` to persist an optional explicit `appointment_id`, enforce Completed + same owner + same pet, refuse unresolved legacy associations, and map the unique-index conflict to 409. The endpoint and relevant dashboard record projections require the prepared medical-link migration before deployment.
- Existing `POST /appointments/create` still validates the owner's pet and server catalog. It continues to reject all booking services while duration rules are absent. No service-management write endpoint was added.
